# 更贴近日常生活的数据建设方案

- 状态：提案，待人工评审，不代表已经上线或开始采集。
- 版本：v0.1，2026-11-09。
- 适用仓库：rizi-city；以编写时主分支 `bb88acf` 为架构基线。
- 本次交付：方案文档和 README 入口。**不新增城市数据，不改现有字段、算法、网页或采集任务，不自动合并。**

## 一、建议先做什么

建议把「我住在这里」和「我在选城市」设为两条核心路径。先建设面向本城居民的城市主页和房价、工资、预期寿命及历史走势概况，再用少量城市验证「每月账单 + 四季生活」两个方向，之后做「医保就医导航」，最后按来源成熟度补「菜篮子」和「街区便利」。目标是同时回答现居居民与准备换城的人真正会遇到的问题：城市概况如何、有哪些适用政策和行动入口、水电气暖怎么算、夏冬有什么生活负担、看病去哪查、买菜价格是否可比、住在哪一片更方便。

第一阶段不增加一个新的城市总分，也不把新的费用直接加到现有「生活成本」里。先让每个数字都有明确对象、适用范围、计算过程和来源，再决定是否适合跨城比较。

提案的核心约束：

1. **公开政策、历史观测、项目情景测算分开。** 「政府规定单价」不等于「当地居民平均账单」；「常年气候」不等于未来天气；「设施名录」不等于当前可用服务。
2. **先做可信的小样板。** 不以填满 20 城为验收目标。来源、许可或维护条件不够的模块保留缺失。
3. **按户、按人、按面积、按月、按采暖季分别记录。** 不在展示时悄悄换口径。
4. **先授权来源，再公开分发。** 能打开、能下载、允许自动取数、允许随开源仓库再分发，是四个不同问题。
5. **本提案不是执行授权。** 后续改 schema、做计算器、补真实数据、扩展来源白名单，都另开可审核的 PR。

## 二、把已经在这里生活的人放到主路径

### 2.1 两条入口共用数据

当前首页以应届生、考公考编、自由职业和跨城排名为主，容易让人以为只有搬家前才需要这个产品。建议后续把一级入口调整为：

- **我住在这里**：选城市 → 看城市概况 → 看适用政策 → 找可办事项与近期变化。
- **我在选城市**：选择候选城市和关注点 → 比较同口径信息 → 深入查看同一份城市主页。

这是一项产品建议，本次不改首页。城市可以存在浏览器本机，默认不要求注册、定位、填学历或提供收入；要跨设备保存、订阅消息或使用定位时再另行设计权限，不自动开通。

两条路径共用同一城市 ID、同一事实版本、同一政策记录和来源。不另建「居民版数据」副本。区别在于筛选、解释和行动顺序，而非对同一个数字提供两套值。

### 2.2 城市主页的信息架构

| 区块 | 居民想知道什么 | 最小展示 | 不能造成的错觉 |
|---|---|---|---|
| 城市概况 | 我生活的城市大致怎样 | 房价、租金、工资平均数/中位数、居民收入消费、出生时预期寿命；有合格历史数据才画折线 | 居民人均可支配收入不叫工资；挂牌房价不叫成交价 |
| 和我有关的政策 | 哪些可能与我有关 | 用户自选职工/灵活就业/待业、租房/有房、应届/非应届等情境；可跳过 | 没填条件不等于不符合；不能保证资格 |
| 最近发生的变化 | 哪个规则变了，什么时候影响我 | 发布日、生效日、具体改动、适用对象、来源；政策与数据更新分开 | 重新核验旧文件不叫新政策 |
| 现在能办什么 | 我需要做什么、在哪里办 | 关键条件、所需材料类别、办理期限、官方入口、最后核验日 | 有入口不等于能办成；不代替官方审核 |
| 日常生活 | 账单、气候、看病、买菜和周边 | 本提案的五类生活模块，按本城实际覆盖展示 | 样板片区不等于全市覆盖 |
| 数据和反馈 | 这个数字能相信吗 | 来源、缺口、纠错入口和版本 | 没找到不叫没有，更新日期不叫适用年份 |

城市概况先用卡片和短说明，长表按需展开。首屏要能区分「已核实」「待核实」「过期」「尚未覆盖」，不能为了整齐把缺失填成 0。

### 2.3 个人情境只辅助筛选

可以提供「普通在职租房者」「自由职业者」「已经有房」「刚失业」等快捷情境，但它们只是可编辑筛选，不是系统对用户的身份认定。是否需要年龄、户籍、参保地、毕业年份等，取决于具体政策；默认少问，进入特定事项后再问必要条件。

匹配结果分三类：

1. **可能适用**：已知条件满足，仍需官方确认。
2. **还需确认**：缺少某个条件，明确指出，不能自动排除。
3. **目前不匹配**：具体哪条已知条件不满足，并给原文。

不收集身份证号码、精确住址、工资单、疾病或家庭证明来「完善画像」。偏好和条件默认本地保存并可清除；分享城市页不携带个人条件。个性化订阅、定位和账户体系均不在第一版必需范围。

### 2.4 政策不是新闻流，要能落到行动

未来政策记录可在现有字段之上设计可复用的 `policy_id`、`topic`、`audience`、`geographic_scope`、`eligibility_rules`、`benefit_type`、`application_window`、`official_action_url`、`published_at`、`effective_from`、`valid_until`、`supersedes` 和证据字段。

现有落户、人才补贴、灵活就业等记录先映射到明确主题，不强行改名成面向全体居民的政策库。后续住房公积金、失业保障、保障性住房、家庭服务等需要独立选题、来源核验与实施 PR，不因本方案出现栏目就自动开始填数。

每张行动卡要回答「谁可能适用、能做什么、什么时候做、需要先确认什么、官方在哪里办」。截止日必须区分固定日期、毕业/参保后若干月、持续受理；无明确截止日则写未见固定截止日期，不制造紧迫感。

近期变化按真实发布/生效事件排序，另列「资料核验更新」。例如旧补贴页面今天重新打开，只更新核验记录，不推送「今天新增补贴」。征求意见、已发布待实施、正在实施、已到期、已被替代分开。

### 2.5 现有功能的两个重要适用范围

- `subsidy_scan.living_none / rent_none` 表示查过后确认**没有面向普通应届生的市级现金生活/租房补贴**，还排除了区级、行业限定和实物配租等。居民页只能按这个原范围呈现，不能写「这个城市没有补贴」或「你没有补贴可领」。
- 日子指数 v0.1 使用本科落户、本科补贴和灵活就业社保等条件。它适合特定比较视角，不能在居民主页顶部变成适用于所有人的「城市得分」。居民主页先显示事实概况；如保留指数入口，必须说明视角并链接方法。

### 2.6 居民路径的 MVP 和验收

首个产品实现建议只做到：城市选择/本机记住城市、城市主页、已有政策按原适用范围分类、来源与变更日期、官方行动入口，以及房价/工资/预期寿命可得性卡；有已核验历史资料的指标再加折线。先不做账号、消息推送、全国政策抓取或资格自动审批。

MVP 采用少量试点城市，与账单和气候样板共用试点。即使工资中位数暂不可得，也应明确显示「未找到同口径公开数据」，不隐藏这个用户关心的问题。

验收：至少5位已在本城生活、非应届人群的试用者，能在3次导航内找到相关官方入口，或正确识别尚未覆盖/没有已核实适用事项；看懂一个城市概况数字的口径，并辨别「可能适用」不等于「已确认资格」。同时确认跨城比较没有出现另一份重复且不同步的数据。产品测试失败时先调整信息架构，而非继续堆字段。

## 三、和现有功能的边界

### 3.1 已有能力和本次增量

| 现有内容 | 目前口径 | 生活数据的增量 | 避免重复的做法 |
|---|---|---|---|
| `living.rent_avg_per_sqm` | 监测机构住宅平均租金，元/㎡/月 | 账单按实际租赁条件计算，展示「房租是否含水电暖」 | 不另建房租数据库；复用现有值并保留月份与监测口径 |
| `living.consumption_per_capita` / `income_per_capita` | 统计公报居民年消费支出/年可支配收入 | 可编辑的家庭现金预算 | 统计参照和个人预算分屏，不相加、不称为个人工资 |
| `flexible_employment` | 灵活就业养老、医保缴费和办理条件 | 就医时的资格、报销条件、官方查询路径 | 新模块不重复存医保缴费额，只引用现有来源和字段 |
| `floor` / `freelance_floor()` | 社保 + 30㎡折算租金 | 单列水电气暖及其他项目的预算视图 | 保留旧底线定义；新增视图叫「情景预算」，不能悄悄替换 |
| 日子指数 v0.1 | 房租负担、消费/收入、落户、补贴、社保；通勤暂停 | 气候偏好与街区设施的独立说明 | 本阶段不加权、不改排名、不把缺失当低分 |
| `commute` | 待建立统一来源，当前暂停使用 | 住址周边设施或步行路网可达性 | 不把街区步行时间当城市平均通勤时间 |
| Roadmap 成家、小城、被裁 | 尚待开发的人群入口 | 将来可复用账单、医保和公共服务模块 | 本阶段不顺带扩展购房、育儿、失业金政策 |

架构依据见 [`_template.yaml`](../data/cities/_template.yaml)、[`scripts/build.py`](../scripts/build.py)、[`docs/index-method.md`](index-method.md) 和 [`site/README.md`](../site/README.md)。

### 3.2 必须防止的收入支出重算

国家统计局将食品、居住、医疗等计入居民消费支出；其中居住包含房租、水、电、燃料、物业和自有住房折算租金。可支配收入也不等于税前工资，转移净收入中已扣除税款和社会保障等转移支出。[S1]

因此禁止以下做法：

- `总生活费 = 人均消费支出 / 12 + 房租 + 水电气 + 菜篮子`。这些支出已经部分或全部包含在消费总额中。
- `个人结余 = 城市人均可支配收入 / 12 - 全部个人费用`。居民平均数不能代表用户收入，而且统计数包含非现金项目。
- 从用户已经扣完社保的到手收入里，再扣同一笔职工社保；把灵活就业医保再计入「医疗支出」一次。
- 用燃气壁挂炉取暖时，既计取暖用气，又加集中供暖费；空调用电已经进电表后，再加一份「夏季制冷费」。
- 房租已包物业/水/暖时继续逐项增加；把食品篮子当成全部餐饮费，又把包含同批采购的自报伙食费加一遍。

未来预算采用三层展示：

1. **统计参照**：原有居民收入、消费和指数，只解释，不参与现金合计。
2. **已覆盖项目小计**：用户明确选择的房租、账单、社保等互斥项目。缺项必须列出，不能称为「完整生活费」。
3. **个人现金余额**：仅在用户主动输入自己的现金收入、已扣项目、账单和其他支出后计算。自由职业输入须说明是营业额还是扣除经营成本后的收入；税前收入未经完整税费模型处理不显示税后结余。

每笔费用应有 `expense_category`、`included_in`、`paid_by` 和 `already_deducted`。同一费用最多计一次；不确定是否包含时先不算合计，并解释需要确认什么。用户输入默认只在本机使用，不进入公开数据。

## 四、补齐房价工资寿命与历史走势

这些概况指标直接服务「我已经住在这座城」的人，也服务跨城比较。建议列为居民城市主页的 P0 基础能力：先定义并展示能查到什么，再补真实数据；未找到可靠中位数时，明确留空比估一个数更有用。

### 4.1 房价必须说明在描述哪一种市场

| 指标 | 能回答的问题 | 不能替代什么 |
|---|---|---|
| 新建商品住宅成交均价 | 某期新房成交的总体价格水平 | 不能代表二手房、某套房、挂牌价或全体住宅存量 |
| 二手住宅成交价 | 特定覆盖范围内的实际成交水平 | 需要明确登记/网签口径、样本与地域，不能混入新房 |
| 挂牌价 | 卖方报价或平台挂牌样本 | 不等于最终成交；下架不等于售出 |
| 住宅销售价格指数 | 同比、环比和定基变化 | 不是元/㎡价格；不能从指数倒推城市房价 |
| 区域/户型中位价 | 明确样本分布的中间位置 | 不可由全市均价、价格指数或单个区间反推 |

优先地方住建/房管公开网签、交易和统计资料；国家统计局70城价格指数用于走势，不填充绝对房价。[S12] 平台挂牌监测只有在覆盖、去重、更新时间和许可明确后才考虑，不能因可搜索就抓取并公开打包。

建议字段：`market_segment`（新房/二手房）、`property_type`（住宅/商品住宅等）、`price_basis`（成交/网签/挂牌/指数）、`statistic`（均价/中位数/指数）、`value`、`unit`、`period`、`geographic_scope`、`area_basis`、`sample_count`、`sample_coverage`、`aggregation_method`、`total_value`、`total_area`、`revision_status`，以及通用来源字段。

若官方只给同地域、同期间、同住宅分类的销售额和销售面积，可在**将来获批的派生层**计算面积加权的销售均价，并显式标为派生值。假设销售额100亿元、销售面积100万㎡，相除为10,000元/㎡；这是虚构单位测试。它不是每套房价格的简单均值或中位数，混合商业用房的总额/面积更不能叫住宅均价。未售样本、户型/区位构成变化也会影响这个值，不能据此推断同一套房涨跌。[S15]

第一版不预测房价、不推荐买卖时机，不给个人按揭或贷款资格结论。新增房价不会自动进入日子指数；将来若做房价收入比，必须先解决家庭/个人、税前/税后、面积假设与统计时间匹配。

### 4.2 平均工资和中位工资分开存

用户关心的「平均工资」至少有以下口径，不应混在同一栏：

- 城镇非私营单位就业人员平均工资。
- 城镇私营单位就业人员平均工资。
- 特定行业、职业或岗位样本的平均/中位工资。
- 在岗职工与全部就业人员口径，须按来源原名标注；广州官方同页分别列示，不能混用。[S16]
- 招聘平台职位报价，属于招聘样本，不是实际已发工资。

国家统计局单位工资统计有特定调查范围，平均工资通常包含代扣的个人所得税、社会保险和住房公积金等，应按税前统计理解，不能标成「到手」。[S13] 城市居民人均可支配收入覆盖的人群与收入来源不同，继续使用现有 `income_per_capita` 名称，不复制到工资字段。

**中位数必须有同口径来源。** 国家或地方公布的居民人均可支配收入中位数不是工资中位数；某职业调查的50分位工资也不能冒充全市所有劳动者中位工资。[S14] 找不到全市口径则保存 `value: null` 与原因，可另列合格职业样本的中位数，但不能仅显示一个醒目的「本市中位工资」。

建议字段：`population_scope`、`unit_ownership`、`industry`、`occupation`、`employment_definition`、`statistic`（mean/median/p25/p75）、`gross_or_net`、`annual_or_monthly`、`includes_bonus`、`includes_employee_contributions`、`value`、`unit`、`reference_year`、`published_at`、`sample_size`、`survey_method`、`coverage_exclusions`、`source_id`、`missing_reason`。

若将年平均工资除以12，展示为「年工资折合月均」，不是每月工资条或平均到手。奖金、发薪月数和个人税费可能不同。平均数和中位数并排时，必须是相同人群、地区、时间和统计方法；否则拆开卡片并禁止算「均值高出中位数多少」之类比较。

### 4.3 来源更新和验收

- 房价：随官方月度/季度发布更新，展示资料期而非仅显示今天核验；重复挂牌去重、样本变化和修订方法必须可解释。
- 工资：年度资料发布后核验；记录数据年与发布年。年度滞后是统计发布特点，不通过猜测填成今年。
- 中位数：每轮调查官方是否发布；未知记录查过的来源和范围，不写「这个城市永远没有中位数」。禁止由均值乘系数估算。
- 房价绝对数与指数、工资均值与居民收入、样本中位数与全体劳动者中位数，须有独立字段与明显标签。
- 验收至少覆盖：单位换算、年度/月度标签、资料年份不同、统计范围不同、来源被修订、中位数缺失、均价只覆盖部分城区等情形。

### 4.4 预期寿命可以放，但不是个人寿命预测

建议城市概况增加「出生时预期寿命」资料卡，作为城市公共健康的长期背景指标，不与工资、房价混成一项即时生活评分。它是根据特定时期各年龄死亡水平构造的统计指标，不是对某个居民还能活多久的预测，也不是当年死亡人口的平均年龄，更不代表搬到该城市能多活多少年。[S19]

必须保留：`indicator_definition`（出生时/某年龄预期寿命）、`population_scope`（户籍/常住等）、`sex_scope`、`reference_year`、`geographic_scope`、`method`（来源有披露才填）、`value_years`、`published_at`、`source_id`、`revision_status`。官方没有说明人口范围或方法时，显示「口径未说明」，不加入跨城排名。

城市卫生健康部门的年度公报可作为候选来源，但需逐年核对是否仍是同一人口范围。[S20] 一个城市公布户籍人口预期寿命，另一个是常住人口，不能只因单位同为“岁”就比较优劣；性别分组与总体也不能混用，总体值不得用男女寿命简单平均代替。缺年留空，不用全国、省级或邻城数据替代。

首版只做公开统计概况，不推断居民疾病、健康风险或医疗水平的单一因果。阶段性冲击、统计修订和人口构成变化可影响数据，解释以发布机构说明为准。

### 4.5 历史折线图作为概况卡的展开视图

用户应能看出「最近一个数」从哪里来、过去怎样变化。建议房价、租金、工资、居民收入消费、预期寿命等在有可靠历史资料时提供折线图；没有合格序列时显示单点和缺失原因，不为图形好看补齐年份。

| 主题 | 推荐频率与单位 | 连线规则与关键提示 |
|---|---|---|
| 住宅价格指数 | 月度；同比/环比或定基指数 | 不把环比指数与定基指数连成一条线；更换基期或方法时标注，不自行拼接 |
| 住宅成交均价/租金 | 月度或季度；元/㎡（租金另含/月） | 成交/挂牌、新房/二手房、样本范围分系列；没有同口径数据的期间断开 |
| 平均/中位工资 | 年度；元/人/年 | 私营/非私营、就业/在岗、职业分组分别绘制；只有同总体时才并列比较均值和中位数 |
| 居民收入消费 | 年度；元/人/年 | 城镇/全体居民分开；不要叫工资走势图；名义值不标成已扣通胀 |
| 出生时预期寿命 | 年度或官方实际公布年份；岁 | 户籍/常住、总体/男/女分系列；断年不插值，不外推未来 |
| 气候/价格篮子 | 气候月度常年分布；篮子周/月观测 | 气候12个月季节曲线不是历史年份变化图；篮子更换规格/权重须另起版本 |

历史观测记录至少包含：`series_id`、`indicator_id`、`period_start`、`period_end`、`frequency`、`value`、`unit`、`population_scope`、`geography_version`、`method_version`、`base_period`、`source_id`、`release_date`、`revision_of`、`missing_reason`、`comparability_group`。

实施规则：

1. `null`、未发布、访问受阻、许可不明和口径不可比都不画成0。缺失点断线，不向前填充、不插值、不将年度值复制12次做月线。
2. 只在同一 `comparability_group` 内连接相邻合格观测。统计范围、单位、区域边界、指数基期或篮子组成变化时标记断点；官方提供可比回溯序列时，注明修订后再接续。
3. 保留当期发布值与官方修订关系，图上默认最新官方修订版，查看详情可知发布时间和修订日；不把新发布日期当观测年份。
4. 同比/环比由来源给出优先；自行计算时必须有可比基期且说明方法。缺上一期不输出涨幅，基数为0时不计算百分比。
5. 房价走势优先可比价格指数，混合成交均价只解释成交结构。没有官方衔接系数时不把不同基期指数机械接上；新基期本身不是涨跌。
6. 同屏默认一类单位，避免工资和房价双轴制造关系。Y轴如非从0开始必须清楚显示刻度；寿命小幅变化不能靠窄轴渲染为剧烈变化。
7. 点选/键盘聚焦显示数值、统计对象、资料期、来源、核验状态；提供同等可读的表格与缺失说明。下载只含许可允许再分发的公开数据。
8. 图的时间窗口由合格历史数据决定，可先显示近5年或近24个月；不足时照实显示，不承诺每城都有完整10年序列。

历史数据往往来自旧年鉴、附件或已撤下页面，可能比最新值更难核验。先对每个指标做年份覆盖清单和授权评估，再排图表实现；未核验的搜索摘要不进入折线。历史寿命指标不是年度必更的强承诺，以官方发布节奏为准。

## 五、五个方向的优先级

以下评分是产品判断，不是实证测量。价值、可获得性、可比性越高越好；维护成本和误导风险越高越需要后置。

| 方向 | 用户价值 1–5 | 可获得性 1–5 | 可比性 1–5 | 维护成本 1–5 | 误导风险 1–5 | 建议顺序 |
|---|---:|---:|---:|---:|---:|---|
| 水电燃气供暖账单 | 5 | 4 | 3 | 2 | 3 | P0，先规则卡和显式情景计算 |
| 四季气候与生活准备 | 4 | 3 | 3 | 2 | 3 | P0，先官方月度气候资料；授权不明只做资料导航 |
| 医保就医导航 | 5 | 4 | 2 | 4 | 5 | P1，先办事入口和规则，不做万能报销计算器 |
| 菜篮子 | 4 | 3 | 2 | 5 | 3 | P2，有连续零售监测再做固定篮子 |
| 街区便利 | 4 | 2 | 2 | 5 | 4 | P2，先设施目录样板，再谈可达性 |

不先做「幸福感」「宜居度」新总榜。偏好不同、来源覆盖不均、城区与郊区差异大，把五类信息压成一个数容易制造精确感。

## 六、水电燃气供暖账单

### 6.1 用户问题和最小产品

回答「同样用量，在这个收费范围内要交多少」「为什么我的账单与估算不同」「冬季一次要准备多少钱」。第一版输出：适用条件、官方计价规则、可编辑用量、月度现金支出与全年摊销、尚未计入的费用、来源和日期。

不输出「某城市单人水电费平均为 X 元」，除非确有同口径家庭调查。示例用量只能叫项目预设或用户输入，不能冒充当地统计平均值。

### 6.2 指标和字段

| 字段组 | 建议字段与类型 | 单位和必填口径 |
|---|---|---|
| 服务对象 | `service_type` 枚举；`customer_type`；`provider`；`service_area` | water / electricity / gas / district_heating；居民/非居民；供应商与具体覆盖区域 |
| 计量周期 | `billing_period`；`tier_reset_rule`；`effective_from`；`effective_to` | 月/年/采暖季；自然年还是开户周期；政策生效日期不等于发文日期 |
| 计价档位 | `tiers[] {lower, upper, rate}`；`tier_boundary_rule` | kWh、m³；阈值是每户还是每人；上界是否包含；末档无上限用 null |
| 计费组成 | `price_components[]`；`fixed_charge`；`tax_included` | 基本价格、污水处理费、附加费；必须标明综合价是否已包含，避免叠加 |
| 特殊条件 | `household_size_rule`；`meter_type`；`time_of_use`；`subsidy_conditions` | 多人口扩档、合表/独立表、峰谷时段、补贴条件及是否已享受 |
| 供暖 | `heating_mode`；`area_basis`；`rate_per_area`；`season_rule` | 集中供暖/燃气/电/无；建筑面积或使用面积；元/㎡/采暖季；报停、计量收费另列 |
| 证据与状态 | 本文第十一节通用字段；必要时 `rules[]` | 同市不同供应区分别成记录；无适用政策不等于免费 |

水价的阶梯阈值可能按年，电价和气价也可能按年或按季节分档，不能默认按月重置。阶梯调价遇到跨生效日账期时，要按当地文件的抄表结算规则处理；没有规则就不自动分摊。

### 6.3 计算方式和例子

**以下所有用量、阈值、单价都是假设测试值，与任何城市实际政策无关，不可录入城市数据。**

设阶梯累计费用函数为：

```text
T(q) = Σ max(0, min(q, upper_i) - lower_i) × rate_i
本期阶梯费 = T(周期此前累计用量 + 本期用量) - T(周期此前累计用量)
本期账单 = 本期阶梯费 + 未包含的固定费或附加费
```

例：假设年度第一档 1,200 kWh、0.50 元/kWh，超过部分 0.60 元/kWh；此前累计 1,100，本月 200。应计 `100×0.50 + 100×0.60 = 110 元`，不能把本月 200 全算第一档为 100 元。若不知道此前累计量，显示可适用的档位区间或请用户输入，不伪造确定账单。

另设集中供暖按建筑面积 20 元/㎡/采暖季，房屋 60㎡，则一季 1,200 元。展示同时区分：

- 合同约定缴费月份的实际支付：1,200 元。
- 为全年预算预留：100 元/月，标签为「全年摊销」，不是每月都会收到的账单。
- 仅按四个月供暖期分摊时为 300 元/月，须明确这个分母，不能与全年摊销混称。

假设某个普通月水费 30、电费 110、做饭燃气 30，供暖全年预留 100：项目小计为 270 元/月，其中当月水电气 170、供暖预算预留 100。实际集中缴暖费的月份现金需求可能为 1,370 元。页面要分别显示两种视图，不能相加为同一种月费。

如租金已含供暖则供暖增量为 0，但界面须写「已含在租金」，不是「当地免费供暖」。无集中供暖的住房不自动推断冬季没有取暖支出。

### 6.4 来源、更新和测试

优先地方发改部门正式价格文件，再用政府门户或官方供应企业说明核对执行范围。具体已核验示例见 [S2]–[S5]。企业官网并不都在现有 `*.gov.cn` 白名单内；将其变成数据来源前须单独审批并修改相关规范，不能只改校验器放行。

- 拟定巡检：每季度查一次有效文件；取暖政策在采暖季前再查一次；收到正式调价信息时专项复核。不是每季度覆盖旧日期，而是打开原文确认现行性。
- 更新触发：新文件、生效日、供应区域/人口档变化；公告「拟调整」「征求意见」不得当成已实施价格。
- 必测：阈值前/恰好等于/刚超过、跨年、峰谷、多人口、合表、租金包费、未满账期、负数与极端用量、币种和小数舍入。
- 先支持简单居民独立表规则。无法清楚编码的合表、公寓商业水电、热计量结算等先提供官方说明，不硬套简化计算器。

## 七、四季气候与生活准备

### 7.1 从天气数值转成生活问题

回答「哪几个月通常更冷、更热、更湿」「需要提前考虑防潮、取暖或制冷吗」。优先展示 12 个月温度、降水和观测时段，再配基于明确规则的提示，不直接给「最舒服城市」排名。

将三种时间尺度分开：气候常年值、具体年份观测、近期天气预报。第一版不提供天气预报，也不把某年极端事件称为常态。四季标签可作为阅读分组，但保留月度数据；不强行用统一四季日期描述所有气候区。

### 7.2 指标口径

| 指标 | 定义与单位 | 可接受来源与限制 |
|---|---|---|
| 月平均温度 | 同一站点和基准期的月平均气温，℃ | 同时保留站号、经纬度、海拔、基准期和版本；市中心不等于全市 |
| 月平均最高/最低温 | 月内日最高/最低气温的多年平均，℃ | 不能与当月绝对极值混用；字段名需区分 |
| 月降水量 | 基准期内相应月份降水量的多年平均，mm | 月量不是降水日数；降水日要另记阈值 |
| 降水日/高温日/低温日 | 如日降水达到特定阈值、日最高温达到特定阈值的日数 | 必须有日数据或原发布统计；不能从月均温推算高温日 |
| 湿度或日照 | 相对湿度 %；日照时数 h | 仅当来源、时间聚合和缺测规则清楚时加入；不从降水量推导湿度 |
| 体感相关指标 | 可选的模型结果，带公式版本与适用条件 | 先不做；温湿度必须同地点同时间，不能把各自月均值随意拼成热指数 |

建议字段：`station_id`、`station_name`、`latitude`、`longitude`、`elevation_m`、`normal_period`、`observation_period`、`month`、`metric`、`value`、`unit`、`valid_years`、`missing_rule`、`source_dataset_version`、`spatial_representativeness_note`。

### 7.3 数据可得性与产品降级

中国气象数据网提供地面气候标准值目录，但本次核验到的相关页面有实名科研教育访问限制。[S6] **本提案不假设已取得数据，也不承诺其可商用或可随 CC BY-SA 仓库公开分发。**

优先找地方气象部门公开气候公报/气候概况；这些资料也须逐项查许可和基准期。只有年度公报时，可做「某年气候回顾」，不改标为 30 年常年值。候选数据不可再分发时，只展示允许引用的概要和官方入口，或暂停模块。

城市比较须使用同一指标、同一基准期和可解释的站点代表性。缺一个月不能填 0；缺一个城市不能借邻市替代。不同基准期并排时明显标为不可直接比较，默认不排序。

### 7.4 展示和计算例子

**假设测试数据**：某站某月常年均温 28℃，月降水量 180 mm。可展示「这个月通常较热，雨量较多，出行可留意防晒和雨具」，同时显示统计时段和来源；不能由此宣称「每天闷热」「预计电费增加 100 元」。

若未来加入制冷/采暖度日，须在独立方法文档规定基准温度、逐日输入、缺测门槛与适用目的。它们衡量温度需求，不直接等于家庭用电量。估算空调费用还需功率、能效、保温、使用时长等用户假设，不从气温一项给出确定金额。

拟定维护：每年检查气候公报；常年值仅随数据集版本更新。每次记录新旧基准期和可比性变化，不将新核验日期伪装成新观测年份。

## 八、医保就医导航

### 8.1 先解决规则和路径，不承诺报销结果

现有 `flexible_employment` 回答「怎么缴、缴多少」，新模块回答「参保后去哪查待遇」「异地就医需不需要备案」「哪些官方入口能查定点机构」。首版不接收身份证、医保账号、病历、处方或诊断，不判断具体疾病该怎么治疗。

采用「参保地 + 险种 + 就医地 + 场景」四层入口，至少区分职工/居民、在职/退休、本地/跨省、普通门诊/门诊慢特病/住院。只问完成导航必需的信息，不把某个城市一个报销百分比当成通用待遇。

### 8.2 拟记录字段

| 字段组 | 关键字段 | 展示约束 |
|---|---|---|
| 适用人群 | `insured_region`、`scheme`、`employment_status`、`eligibility`、`waiting_period` | 待遇享受条件和等待期不得藏在脚注 |
| 服务场景 | `care_region`、`care_setting`、`facility_level`、`network_status` | 医院等级不等于所有科室或项目均可直接结算 |
| 费用规则 | `deductible`、`deductible_period`、`eligible_scope`、`reimbursement_rate`、`cap`、`cap_basis` | 起付线按年还是按次；封顶线限制的是费用还是基金支付 |
| 转诊与备案 | `referral_required`、`filing_required`、`filing_validity`、`exceptions` | 紧急就医等例外要有官方依据；不能用一般规则阻碍及时就医 |
| 办事路径 | `official_query_url`、`filing_guide_url`、`local_policy_url`、`contact_channel` | 平台入口与具体政策来源分开；不保存用户登录信息 |
| 来源版本 | 第十一节通用字段；`policy_year`、`effective_from`、`supersedes` | 国家框架不能替代参保地待遇细则；失效政策退出当前规则 |

跨省直接结算的国家文件规定了就医地目录与参保地待遇等分工，且有分类适用条件。[S7] 页面必须让用户看到这两个地点各自决定什么，不能只按就医城市决定报销比例。

### 8.3 测算边界

首版只做规则导航。若后续确需解释报销公式，可提供与真实用户脱钩的教学例子：

**假设**本次总费用 1,000 元，已确认政策范围内金额 800 元，剩余起付线 100 元，简单单段比例 70%，基金剩余额度充足，则示意基金支付 `(800−100)×70%=490 元`，其他支付来源均不存在时个人承担 `1,000−490=510 元`。

必须同时写明：这不是任何城市的实际待遇；不能用 `总费用×70%`；真实结算还受目录先行自付、分段比例、年内累计、个人账户支付、大病保险、医疗救助等影响。凡无法确认规则的情况，不输出个人报销金额。个人账户扣款也不能被误称为统筹基金报销。

维护建议：季度复核，并在年度待遇调整/国家或地方新文件发布时专项更新。不得未经核验抓取个人查询结果；官方页面被登录墙阻挡时只保留导航和限制说明。[S8]

## 九、菜篮子和在家做饭成本

### 9.1 先证明价格可比，再算篮子

回答「同样一篮菜，近期大约多少钱」「哪些品类波动大」。优先地方发改、价格监测中心、商务部门公开的**零售**监测表；农业批发市场、产地收购价只能用于相应市场分析，不能充当居民到手价。

已经核验到有政府价格监测页提供零售表及附件的实例。[S9] 这证明路径存在，不代表所有 20 城都有连续同口径数据，也不代表附件已完成批量授权。

### 9.2 字段与固定篮子

- 原始价格记录：`item_code`、`item_name`、`variety`、`grade`、`origin`（来源提供才填）、`package_size`、`raw_unit`、`raw_price`、`normalized_unit`、`normalized_price`、`market_stage`、`market_type`、`sample_area`、`sample_count`、`aggregation_method`、`observation_date`、`release_date`。
- 不混「元/500g」「元/kg」「元/斤」；单位按原文保留，标准化值注明精确换算。如「元/斤」未明确指市斤，不自动换算。
- 散装鸡蛋与盒装鸡蛋、后腿肉与五花肉、粳米与籼米分别建项目；未知规格不强行映射。
- 篮子是项目公开定义的可编辑采购清单：`basket_version`、每项规格和数量、用途与覆盖天数、替代规则。数量不声称满足营养建议，也不自动按人口线性倍增。
- 先支持一个基础篮子和用户自定义量；不同时维护大量饮食画像。

**假设测试值**：大米 2 kg × 5 元/kg、鸡蛋 1 kg × 12 元/kg、某指定蔬菜 3 kg × 4 元/kg，篮子小计为 34 元。这只是这三项采购，不是每周全部伙食费，也不包括外食、调料、损耗、配送费。它与账单中的做饭燃气是不同费用，但不能再加到已包含采购的用户伙食预算上。

### 9.3 时间、缺失和比较规则

拟先用周频展示，保留各价格实际观测日期。一个篮子的价格窗口、规格映射和聚合方法必须一致：优先同日同份监测表；跨日时限制在预先定义的同一周，并显示最早/最晚日期。

- 指定篮子缺任何必选项：不发布完整篮子价；可展示「已覆盖 X/Y 项小计」，不当作更便宜。
- 不以未说明的邻近品种或邻城价格填补；许可明确的官方修订可回溯更新，保存原因。
- 不把月均价和某一天促销价直接排名；不同样本、市场类型或规格的城市只能并列浏览。
- 拟定周巡检；对于本来每周发布的源，超过两轮发布周期无新记录标「更新延迟」，旧值仅作历史。价格涨跌超过 30% 可触发人工复核，但阈值只是质检线索，不自动判错。
- 连续样板阶段记录取数耗时、断档率和规格不匹配率。如果维护成本过高，降为官方价格周报导航，不做全国榜单。

## 十、街区便利和公共服务

### 10.1 以具体片区为单位

城市均值无法回答「下楼能不能买菜」「晚上附近有没有药店」「图书馆周一开不开」。拟先选择一个城区内少量公开片区，提供菜场、社区卫生服务、药店、公园、图书馆、公交站等目录。不得以城区样板代表全市。

官方「15 分钟生活圈」可作为规划和分类依据，但政策目标、设施名录、现实开放状态、真实步行时间是四种不同证据。官方资料中的示意圈也不能直接当作逐路网实测结果。[S10]

### 10.2 逐级产品，不越过数据能力

| 级别 | 输出 | 必须具备的证据 | 不该声称的内容 |
|---|---|---|---|
| A 官方目录 | 名称、地址、服务类型、官方入口 | 主管部门或机构的公开名录 | 不保证今天开门或还有号源 |
| B 可用性说明 | 预约、开放时间、费用、无障碍信息 | 机构正式页面和核验日期 | 无资料不写「免费」「全天开放」 |
| C 可达性试验 | 从选定公共参考点出发的路网距离/时间 | 合法可用的路网、路由方法、数据日期、入口位置 | 不把圆形半径或直线距离写成15分钟步行 |

字段建议：`facility_id`、`name`、`category`、`address`、`administrative_area`、`location`、`coordinate_system`、`official_url`、`opening_hours`、`appointment_required`、`fee_scope`、`accessibility_note`、`status`、`checked_at`；路由另有 `origin_type`、`routing_source`、`routing_version`、`travel_mode`、`distance_m`、`duration_min`、`route_date`、`assumptions`。

北京市公共数据平台的公园名录已有文件API说明，但本次只核验了文档和认证要求，未取得文件或再分发授权。[S17]

地址解析、POI、地图瓦片和路由 API 都有各自许可、缓存和再分发限制，不因网页能显示就批量搬进 GitHub。不同坐标系统须明确转换依据和许可，不直接混用；避免在未审核情况下建设或发布地图服务。

### 10.3 展示例子与隐私

**假设测试例**：某公共参考点到菜场路网 750 m，以假设步行速度 75 m/分钟得到约 10 分钟。必须标明估算、参考点、方法与未计入红绿灯/台阶等条件；只有直线 750 m 时只能叫直线距离，不能显示上述步行时间。

默认使用社区公共点或用户主动选择的地点，不采集真实住址轨迹。后续若调用第三方定位或路线服务，先说明地点数据将发给谁，并按产品权限要求处理；精确地址不入公开仓库、不进入可分享 URL。

拟定每季度核验目录，开放时间按月抽查；临时停业和服务调整只能标注最后核验时间，不宣称实时。机构目录通常不能证明急诊能力、药品库存或当前挂号余量。

## 十一、数据模型与来源证据

### 11.1 保留现有链路，新增模块独立演进

现有链路是 `data/cities/*.yaml → scripts/build.py → site/data/cities.json → site/app.js / skill query.py / 离线版`。当前 `living` 段主要是租金与统计值，只有少量共有状态字段，不适合塞进高频菜价或大量设施。

建议后续采用独立目录，保持旧数据向后兼容。以下仅为未来布局草图，本次不创建这些文件：

```text
候选目录                 角色
 data/life/sources/        来源、许可、适用范围和版本登记
 data/life/overview/       房价、工资、预期寿命的指标与系列定义
 data/life/series/         经许可的历史观测、缺口、口径断点和修订记录
 data/life/utilities/      城市/供应区计价规则
 data/life/climate/        经许可、聚合后的气候资料
 data/life/healthcare/     险种与就医场景政策摘要
 data/life/food/           有限时间窗口的价格观测
 data/life/neighborhoods/  片区设施摘要，不放个人住址
 docs/                    各模块方法与变更说明
```

新增概况和历史序列不直接塞入现有 `living`，不覆盖原居民收入消费值。居民主页读取概况系列的最新合格观测，折线读取同一系列的历史记录，避免最新卡片和历史图两套数据漂移。

稳定城市标识复用当前文件名，不用自由拼写连接数据。省/市/区/供应区另存范围字段；任何拆分合并须版本化。食品历史表不无限增长进主站 JSON；将来按城市/模块拆分产物，离线版只打包许可允许的最新摘要，附版本和日期。

### 11.2 每条事实的通用信封

| 字段 | 说明与规则 |
|---|---|
| `record_id` / `schema_version` | 稳定主键和 schema 版本，不用展示名作为唯一键 |
| `city_id` / `geography` | 与现有城市 ID 连接；附行政/服务区域、范围版本 |
| `value_kind` | `official_rule` / `observation` / `derived` / `scenario`，界面区分，不混在一个数字里 |
| `source_id` / `source_url` | 指向来源登记及具体文档，不只指首页 |
| `source_title` / `issuer` / `document_number` | 文档名称、发布机关、文号；无文号写 null |
| `source_date` / `effective_from` / `effective_to` | 发布、生效、失效分别记录；未知失效日不代表永久有效 |
| `observation_period` / `reference_period` | 观测区间和气候基准期，与发布时间分离 |
| `verified_at` / `verified_by` / `next_review_at` | 打开原文核对的日期、复核角色、下次计划；仅请求成功不能刷新 verified_at |
| `evidence_locator` / `accessed_url` | 具体条款、表号、页码和实际打开链接；附件可与正文分别记录 |
| `status` / `needs_human_reason` / `access_blocked` | 缺失、待核、已核、过期、访问受阻、许可待确认；不强行复用一个城市级状态 |
| `license_id` / `redistribution_status` | 已核授权、仅可链接、待确认、禁止分发；与事实可信度分开 |
| `method_version` / `inputs` | 派生值与情景值必填；每个输入链接到来源版本或显式假设 |
| `supersedes` / `change_reason` | 被替代记录与改动原因；保留历史，不覆盖后失去依据 |

状态可计算，但最终规则须避免多个布尔值互相矛盾。建议以结构化可用性结果给前端 `{value, usable, reason, coverage}`，借鉴现有 `index_inputs()`，同时分清「历史有效」「当前可用」「允许再分发」。

允许原文值与标准化值并存，不直接改写原值。例如把 500g 转 kg 是精确单位转换；「典型单人每月用水量」则是情景假设，必须另存。证据摘录仅保留必要短句，不将完整受限附件作为仓库素材。

### 11.3 对现有规范的影响

当前 [`MAINTAINING.md`](../MAINTAINING.md) 要求照原文、不换算估算，白名单为政府官网和房租指定来源；本提案中的情景计算和部分候选来源**尚不属于已批准的数据采集规则**。

实施前需人工明确批准：

1. 官方原始值仍严格按原文存储；项目计算只进入独立派生/情景层，保留公式和假设。
2. 非 `gov.cn` 的气象数据门户、公用事业官网或地图服务逐源登记审查，不能整体放开任意域名。
3. 新模块不会仅靠 `source_url + verified_at` 就判定可用，必须校验适用范围、有效期、计价/观测口径和分发权限。
4. 将来同步修改模板、校验、构建、网页、skill、离线版和方法文档；本次不更改这些约束。

## 十二、采集核验更新流程

### 12.1 一个来源进入生产前

1. **登记候选**：找到发布机构原文和具体表格，记录来源性质、覆盖范围、更新频率、访问条件和许可。
2. **只读核验**：人工或助手打开原文及必要附件；搜索摘要、媒体转述、未打开的截图不能标「已核实」。验证码、登录墙、403 等不绕过。
3. **确认可用范围**：检查生效日、被替代文件、供应区、险种、计量单位、价格阶段、样本和基准期。不能仅凭标题带城市名就认定覆盖全市。
4. **保留证据**：登记文号、页码/表格定位、访问日期。仅在许可允许时保存来源快照；哈希可以辅助检测改变，不能代替事实核验。
5. **结构化提取**：人工录入起步；规则稳定后才写采集器。自动解析结果留在待审状态，不直接发布。
6. **双重校验**：schema/单位/范围校验 + 第二人对原文复核。新来源、首次公式和医保规则要求 100% 复核；稳定更新至少遵守仓库 30% 抽查，关键计价变化仍全查。
7. **提 PR**：小批量、单模块或单城；提供改动清单、来源、旧新值、适用期、抽查结果和许可结果。只由人工合并。
8. **发布与回退**：构建摘要，保留方法版本；发现错误先下线受影响计算，保留原因，再用修正 PR 恢复。

### 12.2 分模块更新计划

以下是拟议服务水平，实际投入需在试点后确认，不代表已经安排自动巡检。

| 模块 | 例行检查 | 专项触发 | 陈旧数据的处理 |
|---|---|---|---|
| 房价与租金序列 | 按官方/获准来源月度或季度节奏 | 发布修订、覆盖和指数基期变化 | 保留资料期，待审数据不接入当前值；口径改变断线 |
| 工资与居民收支 | 官方年度发布后核验 | 统计总体、行业、定义或历史修订 | 显示资料年；未公开的中位数留空，不沿用往年假装今年 |
| 预期寿命 | 每年检查是否发布，按实际发布节奏更新 | 户籍/常住、方法、地域或历史修订 | 不强求每年有值；原历史点保留，新口径独立序列 |
| 公用事业 | 季度；供暖季前加一次 | 正式调价、生效日、覆盖区变化 | 超过复核窗口标待复核；已知失效或被替代立即停算 |
| 气候 | 年度；数据版本发布时 | 基准期、站点或质控方法变化 | 历史资料可继续展示原时间标签，不能说成最新预报 |
| 医保导航 | 季度；年度政策重点核验 | 待遇、目录、备案或结算规则变化 | 已知过期停展示当前规则；保留官方查询路径 |
| 菜篮子 | 按公开源周频同步 | 缺档、规格变化、异常涨跌 | 两轮发布未更新标延迟，退出当前比较 |
| 街区便利 | 季度目录核验；月度开放时间抽查 | 机构开闭、迁址、预约调整 | 保留最后核验时间；无法证实的实时状态不显示 |

无人负责维护的模块不扩大覆盖。每城/每模块设置采集维护者、领域复核者和许可证复核责任；角色可以由同一位维护者兼任，但首次高风险公式应有独立复核。

### 12.3 质检门槛

- 有值必须有来源、单位、适用对象、时间和事实状态；派生值必须可由锁定版本输入重算。
- `null` 不作 0；已确认「不适用」「已包含」与缺失分别展示。
- 阶梯区间不重叠、不留未解释缺口，费率和量纲匹配；日期逻辑自洽。
- 气候 12 个月完整性与站点/基准期一致；不把缺测日当 0℃或无雨。
- 医保的参保地、险种和场景缺一则禁止个性化结论；封顶口径含糊则停算。
- 菜价按零售/批发、规格、单位、观测窗口分组；跨组比较须明确阻断。
- 设施去重、关闭状态、坐标系统、来源条款分别校验；一个名录不能同时证明开放时间和路线时长。
- 验收输出覆盖率和排除原因，不追求一个掩盖差异的「可信度总分」。

## 十三、展示原则和用户示例

建议将来在城市详情中增加「日常生活」区，移动端先显示四张短卡，长规则按需展开：

1. **账单**：选供应范围、住房及能源方式，输入用量；首屏带「情景测算」标签和未计入项。
2. **四季**：月度概览，常年期/站点和生活准备说明；无需输入个人信息。
3. **看病**：参保地与场景导航，优先跳转官方查询；不把待遇摘要称为承诺。
4. **附近与买菜**：仅对有合格数据的片区/城市显示，覆盖不足时给官方入口。

例如「两个人、整租、独立居民表、房租不含水电、无集中供暖」是用户可编辑情景，不能预设成全城家庭画像。多人合租水电分摊优先用户自选规则，不默认每户阶梯额能按房间单独享受。

每个结果最少显示：适用范围、事实/测算类别、输入与公式、数据时间、最近核验、来源、缺失和误差原因。每张比较卡显示实际覆盖项，避免缺数据的城市看起来更便宜。来源过期、权限未确认和访问受阻用不同说明，不统称「暂无」。

分享和离线版：分享默认仅携带公开的非敏感情景参数，不带收入、住址或健康信息；离线版显示数据版本、生成时间和无法实时核验提示，外部 API 不能调用时不伪装成实时结果。

### 14.2 风险与处置

| 风险 | 容易出现的误导 | 处置 |
|---|---|---|
| 计价误差 | 商业公寓套居民价；年度阶梯按月算 | 先筛适用对象，信息不足停算 |
| 地域混用 | 中心城区供应价覆盖整个地级市 | 记录供应区，未覆盖区域明确排除 |
| 时间错配 | 旧通知被新发布日期重新转载后当新政策 | 原发文、生效、核验日期分开，检查替代关系 |
| 统计和预算混用 | 人均消费再加水电、平均收入等于个人工资 | 独立视图和互斥费用账本 |
| 医疗误导 | 一个报销比例适用于任何人和医院 | 首版导航，关键条件前置；不建议诊疗和用药 |
| 气候误导 | 月均值代表个人体感或未来极端天气 | 写清站点和时间尺度，不给健康或安全保证 |
| 价格失真 | 批发价当超市价；缺商品仍算便宜 | 保留阶段规格，覆盖不完整不排名 |
| 地图和隐私 | 直线距离当步行时间；住址被公开 | 分级能力、独立许可审核、不存个人精确地址 |
| 自动采集失控 | 反爬绕过、访问条款不清、请求太密 | 只使用允许的方式，限频，遇阻停止 |
| 维护失约 | 一次补全后长期无人更新 | 每模块有负责人、复核周期和降级条件 |

不发布具体个人账单、病历、身份证、医保账号或地址样本。即便用户自愿提供，也不把它们用于公开测试；测试只使用明确虚构的记录。

试点城市建议从现有 20 城中筛选：至少一个有集中供暖的北方城市、一个冬季需要自主取暖的城市、一个夏季制冷需求突出的城市。北京、成都、广州可作为**候选**，但只有来源与许可满足要求才选定，不在本提案中承诺覆盖这些城市。

估量工作包：居民主页与政策导航约3–5人日，房价、工资、寿命口径及历史折线/缺失处理约4–7人日；来源/许可和生活模块口径约 3–5 人日，账单与气候样板约 5–10 人日，医保导航约 3–5 人日；菜价和设施先做限时可行性研究再估工。均不含等待授权、持续八周采样或人工评审的日历时间，也不据此自动启动任务。

### 15.2 本次纯文档 PR 的检查方式

校验脚本保持与主分支基线一致，不执行外来 PR 代码。**提交本次文档变更后**，在干净工作树上运行与现有 CI 相同的构建一致性检查；未提交时则先暂存文档，确认构建没有产生额外的未暂存差异：

```bash
bash scripts/check-no-private.sh --all
python3 scripts/validate.py
python3 scripts/build.py
git diff --exit-code -- site/data README.md
python3 skill/rizi-city/scripts/query.py --data site/data/cities.json list
```

README 仅新增方案入口；其自动生成区段应与构建结果一致。核对 PR 的文件清单只含本文和 README，不提交数据、`dist/` 或其它生成物。具体执行结果写在 PR 中，不把尚未执行的检查写成通过。
